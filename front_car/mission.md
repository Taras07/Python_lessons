# Місія проєкту: Car Catalog, фронтенд

## Що ми будуємо

Односторінковий клієнт (SPA без роутингу) для Car Catalog API на FastAPI.

Застосунок дозволяє:
- Переглядати список автомобілів.
- Фільтрувати автомобілі.
- Переглядати сторінки каталогу.
- Додавати нові автомобілі.
- Редагувати наявні автомобілі.
- Видаляти автомобілі.
- Отримувати зрозумілі повідомлення про помилки API.

## Технологічні обмеження (діють для всіх ітерацій)

- Використовувати тільки vanilla HTML, CSS та JavaScript.
- Не використовувати фреймворки, сторонні бібліотеки та білд-інструменти: npm, webpack, Vite тощо.
- Фронтенд складається рівно з трьох файлів:
  - `index.html`
  - `style.css`
  - `app.js`
- Усі три файли розташовуються в корені фронтенд-проєкту.
- Кожна наступна ітерація розширює ці самі три файли. Не створювати додаткових файлів фронтенду.
- Усі HTTP-запити до бекенду виконувати через `fetch()`.
- Базова адреса API: `http://127.0.0.1:8000`.
- Не змінювати бекенд без окремої вказівки.
- Не додавати функціональність, яка не передбачена поточною ітерацією.

**Примітка:** `mission.md`, `roadmap.md` та файли `spec.md` є технічною документацією проєкту. Вони не входять до трьох файлів фронтенду.

## API, з яким працюємо

Бекенд побудований на FastAPI. Усі маршрути та поля необхідно узгоджувати з фактичною реалізацією бекенду й актуальними Pydantic-схемами.

Базова адреса: `http://127.0.0.1:8000`

### Основні ендпоїнти

- `GET /cars/` - отримання списку автомобілів.
- `GET /cars/{id}` - отримання одного автомобіля за його ID.
- `POST /cars/` - створення нового автомобіля.
- `PATCH /cars/{id}` - часткове оновлення автомобіля.
- `DELETE /cars/{id}` - видалення автомобіля.

### Поля автомобіля

Основні поля моделі `Car`:

- `id` - унікальний ідентифікатор автомобіля.
- `brand_model` - марка та модель автомобіля.
- `manufacturer` - виробник.
- `vin` - ідентифікаційний номер автомобіля, 17 символів, унікальний.
- `body_type` - тип кузова.
- `engine_volume` - об'єм двигуна, необов'язкове поле.
- `horsepower` - потужність двигуна, необов'язкове поле.
- `price` - ціна автомобіля.
- `rating` - рейтинг автомобіля, необов'язкове поле.
- `is_available` - ознака доступності автомобіля.
- `description` - опис автомобіля.
- `year` - рік випуску.
- `options` - додаткові опції автомобіля у форматі JSON.
- `created_at` - дата та час створення запису, якщо поле передбачене актуальною моделлю.

Склад полів для створення, редагування та відповіді API визначається відповідними Pydantic-схемами. Не передавати `id` або `created_at` у запиті створення, якщо цього не вимагає контракт бекенду.

Типи даних, обов'язковість полів, допустимі значення та обмеження валідації мають відповідати актуальним моделям і схемам.

### Фільтрація та пагінація

- Фільтри застосовуються через query-параметри `GET /cars/`.
- Для фільтрації можна використовувати марку та модель, доступність і мінімальний рейтинг, якщо ці параметри підтримуються бекендом.
- Пагінація використовує параметри `limit` та `offset`, якщо саме такий механізм реалізований у бекенді.
- Розмір сторінки за замовчуванням для інтерфейсу: 10 автомобілів.
- Під час переходу між сторінками застосовані фільтри мають зберігатися.

**Важливо:** точні назви query-параметрів, значення за замовчуванням та формат відповіді `GET /cars/` потрібно звірити з актуальним роутером. Фронтенд не повинен надсилати параметри, які бекенд не підтримує.

### Очікувані HTTP-статуси

- `200 OK` - успішне отримання даних або оновлення, залежно від реалізації ендпоїнта.
- `201 Created` - автомобіль успішно створено.
- `204 No Content` - автомобіль успішно видалено, якщо саме такий статус повертає бекенд.
- `404 Not Found` - автомобіль не знайдено.
- `409 Conflict` - конфлікт унікальності VIN.
- `422 Unprocessable Entity` - дані запиту не пройшли валідацію.
- Мережева помилка - сервер недоступний або запит не вдалося виконати.

Фактичні статуси та формат відповідей необхідно перевіряти за реалізацією бекенду.

## Як ми працюємо: ітеративний Spec-Driven Development

Розробка ведеться невеликими ітераціями. Кожна ітерація має конкретну мету, визначений обсяг робіт та критерії приймання.

### Призначення документації

- `mission.md` - фіксує мету проєкту, технологічні обмеження та загальні правила взаємодії з API.
- `roadmap.md` - містить послідовність запланованих ітерацій.
- `spec.md` - описує завдання конкретної ітерації, що потрібно додати, що не входить до її меж і як перевірити результат.

Ці документи є технічною документацією, а не додатковими файлами фронтенду.

### Правила виконання ітерацій

- Реалізовувати лише функціональність, описану в поточному `spec.md`.
- Не переходити до наступної ітерації, доки поточну не реалізовано та не перевірено.
- Не переписувати код попередніх ітерацій без необхідності.
- Не змінювати структуру проєкту, технологічний стек або контракт API без окремої вказівки.
- Якщо вимога суперечить актуальному бекенду, спочатку повідомити про невідповідність, а не вигадувати відсутню функціональність.
- Якщо інформації недостатньо для коректної реалізації, зазначити, що потрібно перевірити, перш ніж змінювати код.
- Після завершення ітерації перевіряти нову функціональність і роботу функцій попередніх ітерацій.

## Загальні вимоги до інтерфейсу

- Інтерфейс має бути зрозумілим і послідовним.
- Картки автомобілів, форми, кнопки, фільтри та модальні вікна повинні мати узгоджене оформлення.
- Інтерфейс має коректно відображатися на різних розмірах екрана.
- Помилки API повинні супроводжуватися зрозумілими повідомленнями для користувача.
- Після створення, редагування або видалення автомобіля інтерфейс має оновлюватися без повного перезавантаження сторінки.
- Стилізація не повинна порушувати роботу форм, фільтрів, пагінації або CRUD-операцій.

## Поточні межі проєкту

У межах поточного проєкту реалізується тільки фронтенд для наявного Car Catalog API.

Не додавати без окремого завдання:
- Авторизацію та реєстрацію.
- Нові ендпоїнти бекенду.
- Нові поля моделі автомобіля.
- Сторонні бібліотеки та фреймворки.
- Додаткові сторінки або клієнтську маршрутизацію.
- Функції, не передбачені затвердженими ітераціями.
